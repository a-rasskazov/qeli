> **Статус документации:** текущая ветка разработки **0.8.2**; планируемый full-IPv6 релиз **0.8.2**;

## 1. Что должно совпадать у клиента и сервера

Почти ничего из этого **не согласуется на проводе** — обе стороны берут значения из
своих конфигов независимо. Поэтому расхождение почти всегда выглядит не как понятная
ошибка «параметры не совпали», а как обрыв на середине подключения.

Самый коварный случай — **`bind_static` (H-1)**: расходятся не проверки, а соли KDF,
поэтому хендшейк формально проходит, а первая же зашифрованная запись не расшифровывается.

| Что | Где у сервера | Где у клиента | Симптом при расхождении |
|---|---|---|---|
| **`bind_static` (H-1)** | `auth.bind_static_to_session` (**по умолчанию `true`**) | `bind_static` (по умолчанию `true`) | Соли KDF расходятся → стороны выводят **разные ключи**. Явной ошибки «параметры не совпали» нет: на сервере `handshake failed for <addr>`, на клиенте — обрыв сразу после `Handshake complete` (`decryption failed`). Самый неочевидный случай |
| **Ключ сервера (пиннинг)** | `qeli show-identity` | `key` / `auth.server_public_key` | `SERVER KEY MISMATCH … possible MITM attack!` — с подсказкой, что делать при ротации |
| **`bind_static` + нулевой ключ** | — | `key = 0000…` (TOFU-заглушка) при `bind_static = true` | Фатально ещё до сети: `bind_static_to_session is on but server_public_key is the all-zero TOFU sentinel` |
| **Транспорт** | `bind.transport` (`tcp`/`udp`) | `proto` | Соединение просто не устанавливается: TCP-клиент стучится в UDP-порт и наоборот |
| **Wire-режим** | `obf.mode` | `mode` | Обычно совпадают. Актуальный Reality использует `reality-tls` с обеих сторон; новый сервер временно принимает legacy server-написание/carrier для миграции. Остальные расхождения дают таймаут хендшейка |
| **`obfs_key` (для `mode = obfs`)** | `obf.obfs_key` | `obfs_key` | Поток расшифровывается в мусор → хендшейк не парсится |
| **REALITY `short_id`** | `obf.tls.reality_proxy.short_ids` | `reality_sid` | Сервер **молча** считает вас чужим и мостит на target: «не подключается, ошибок нет», а `curl` до сервера показывает настоящий сайт |
| **AmneziaWG junk** | `obf.awg.jc` / `jmin` / `jmax` | `awg` / `jc` / `jmin` / `jmax` | Хендшейк не проходит: сервер ждёт другое число junk-пакетов. Включать нужно **на обеих** сторонах с одинаковым `jc` |
| **Часы (для REALITY)** | — | — | Токен несёт timestamp с окном **±120 с**. Разошлись часы → тот же симптом, что и с неверным `short_id`: молча мостит на target. Нужен NTP |
| **Профиль, к которому пиннингуетесь** | у **каждого** профиля свой `identity/<профиль>.key` | `key` | Пин от профиля A против порта профиля B → `SERVER KEY MISMATCH`. Ключ не общий на сервер, а на профиль |
| **`require_client_key_proof`** | `auth.require_client_key_proof` | наличие пина | Обратное направление: сервер отвергает **непиннингованного** клиента — `AUTH DENIED … server key not pinned`, и попытка идёт в счётчик брутфорса по IP |
| **`obf.fronting`** | `obf.obfs_fronting` (по умолчанию `websocket`) | `front` | Для `mode = obfs`: расхождение → `obfs ws: server did not switch protocols` |

**Практика.** Не собирайте клиентский конфиг руками — импортируйте `qeli://`-ссылку
(`qeli add-client <user> --link --host <host>` или кнопка в панели): она несёт `host:port`,
`user`, `pass`, `proto`, `mode`, `key`, `sni`, `reality_sid`, `obfs_key`, `awg`/`jc`/`jmin`/
`jmax` — то есть **все** строки таблицы выше, кроме `bind_static` (он и там, и там по
умолчанию включён) и часов.

Отдельно про роутеры: в шаблоне OpenWrt (`qeli-openwrt/files/qeli.config`) ключ — нулевая
TOFU-заглушка, и `bind_static` под неё выставлен в `'0'`. Как только вы прописываете
**настоящий** ключ, обязательно переведите и `bind_static` в `'1'`, иначе получите строку
1 из таблицы.

## 2. Проверка конфига перед запуском

```bash
qeli check-config --config /etc/qeli/server.conf
qeli check-config --client --config /etc/qeli/client.conf
```

Команда ничего не запускает — ни слушателей, ни TUN, ни службы — и разделяет три вида
проблем, которые обычный старт различить не даёт:

1. **Синтаксис** — сломанная строка с номером.
2. **Схема** — те же проверки, что делает data-plane worker при старте (неизвестный
   `bind.transport`, опечатка в `obf.mode`, `plain` на UDP, нулевая
   явный ноль в `perf.connection.*` и т. д.), поэтому вердикт совпадает с реальным запуском.
3. **Ключи, которых никто не читает** — то есть опечатки.

Третий пункт важнее, чем кажется. **Неизвестный ключ не является ошибкой**: он просто
никогда не запрашивается, и параметр молча остаётся дефолтным — предупреждения нет ни на
каком уровне логирования. Именно так `exclude_routes` вместо `exclude` долго выглядел
рабочей настройкой, пока split-tunnel не применялся вовсе. Теперь это видно:

```
/etc/qeli/client.conf: 1 key(s) that nothing reads — check the spelling:
  [qeli] exclude_routes
An unknown key is not an error: it is simply ignored, and the setting keeps its default.
```

Код возврата: `0` — чисто, `1` — есть проблемы. Годится для CI и для проверки перед
`systemctl restart`.

> Команда проверяет **сам файл конфига**, а не окружение вокруг него. Она не читает
> `users_file`, не проверяет наличие identity-ключа, занятость портов и права на файлы —
> это выясняется только при реальном старте. «OK» означает «конфиг корректен», а не
> «сервер точно поднимется».

> Если версия старше и команды ещё нет, конфиг можно проверить запуском в форграунде
> (`systemctl stop qeli && qeli server --config …`), но прерывать придётся вручную:
> супервизор перезапускает упавший worker по кругу с нарастающей паузой и сам не
> завершится даже на заведомо битом конфиге.

## 3. Обновление и откат

### 3.1. Установка из `.deb` (обычный путь)

В корне репозитория есть [`update-qeli-server.sh`](../../../update-qeli-server.sh) — он
делает всё правильное сам:

```bash
sudo ./update-qeli-server.sh
```

Что именно он делает:
1. Определяет текущую версию и последний релиз на GitHub (`QELI_REPO` переопределяет репозиторий).
2. Качает `.deb` **и `SHA256SUMS`** и **сверяет контрольную сумму** — при несовпадении не ставит.
3. **Копирует текущий бинарь** в резервную копию рядом.
4. Ставит пакет и перезапускает `qeli`.
5. Если служба **не поднялась** — **сам возвращает старый бинарь** и перезапускает снова,
   а если и это не помогло, честно сообщает, что служба лежит, и просит смотреть журнал.

То есть откат при неудачном обновлении встроен; отдельных действий не требуется.
`QELI_FORCE=1` переустанавливает даже текущую версию.

Три оговорки:

- **Откат — только бинаря.** Скрипт не бэкапит конфиг, пользователей и identity-ключ и
  не откатывает метаданные dpkg (пакет числится новым, а бинарь на диске старый). Перед
  крупным обновлением снимите бэкап (см. [§4](#4-что-бэкапить)).
- **`QELI_DEB=/путь/к.deb` отключает проверку контрольной суммы** — сверять нечего.
  Осознанно ставьте так только свои сборки.
- **Сам скрипт проверяет только SHA256** из того же релиза — это целостность, но не
  происхождение: злоумышленник, подменивший релиз, может подменить и `SHA256SUMS`.
  Для Linux-пакета workflow `release-build-and-attest` теперь checkout'ит точный тег,
  собирает `make deb-portable`, прогоняет smoke-проверки пакета, создаёт подписанный
  **build provenance** и только после этого загружает в релиз ровно эти байты и заново
  формирует `SHA256SUMS`:

  ```bash
  gh attestation verify qeli_0.8.1_amd64.deb -R litvinovtd/qeli
  ```

  Эта проверка связывает Linux-пакет с репозиторием, workflow и исходным коммитом тега.
  Для остальных desktop/mobile-ассетов пока остаётся только publication evidence, пока их
  release-сборки тоже не перенесены в CI. У контейнера отдельный build provenance:
  `gh attestation verify oci://ghcr.io/litvinovtd/qeli:latest -R litvinovtd/qeli`.
  Для проверки нужны `gh` и сеть, поэтому апдейтер её не выполняет — запускайте вручную,
  когда нужно независимо подписанное доказательство исходников и сборки.

Ручной эквивалент, если скрипт использовать не хотите:

```bash
sudo cp -a "$(command -v qeli)" /root/qeli.bak      # 1. бэкап бинаря
sudo apt install ./qeli_<версия>_amd64.deb          # 2. установка
sudo systemctl restart qeli && systemctl status qeli
# откат, если не поднялось:
sudo systemctl stop qeli && sudo cp -a /root/qeli.bak "$(command -v qeli)" && sudo systemctl start qeli
```

> **Ваши конфиги пакет не трогает.** `.deb` кладёт только `*.conf.example`; рабочие
> `/etc/qeli/server.conf`, `users.conf` и identity-ключ в пакет вообще не входят —
> перезаписать их нечем. Поэтому «обновление» — это замена бинаря, а не переустановка
> конфигурации.

Три вещи, о которых стоит знать заранее:

- **Не правьте `*.conf.example` на месте.** Они — dpkg-conffiles, и при обновлении apt
  спросит «оставить вашу версию или взять новую». Копируйте (`cp server.conf.example
  server.conf`) и правьте копию — тогда обновления проходят молча.
- **`postinst` делает `chown -R qeli:qeli /etc/qeli` при каждой установке.** Содержимое
  не меняется, но владелец файлов — да. Если вы намеренно выставляли другие права,
  проверьте их после обновления.
- **`apt remove` выполняет `systemctl disable`.** После переустановки автозапуск нужно
  включить снова: `systemctl enable --now qeli`. А `apt purge` **оставляет `/etc/qeli`**
  (в пакете нет `postrm`) — то есть ключи и хеши паролей остаются на диске; удаляйте
  вручную, если этого не хотите.

### 3.2. Docker

Образ не обновляется «на месте» — меняется тег и пересоздаётся контейнер. Состояние живёт
в томе `/etc/qeli`, поэтому конфиги, пользователи и ключ переживают пересоздание:

**Сначала посмотрите, какой образ у вас в `docker-compose.yml`** — от этого зависит команда.
В комплектном compose стоит `image: qeli:latest`, и он **собирается локально**, а не тянется
из реестра. Для него `docker compose pull` бесполезен (и попытается сходить в Docker Hub за
чужим образом) — нужна пересборка:

```bash
docker buildx build -f release/docker/Dockerfile -t qeli:latest --load .
docker compose -f release/docker/docker-compose.yml up -d
```

Если вы переключили `image:` на опубликованный `ghcr.io/litvinovtd/qeli:latest`, тогда
работает обычный путь:

```bash
docker compose -f release/docker/docker-compose.yml pull
docker compose -f release/docker/docker-compose.yml up -d
```

Откат — вернуть предыдущий тег образа в `docker-compose.yml` и повторить `up -d`.
Подробности и оговорки — [release/docker/README.md](../../../release/docker/README.md).

> **`update-qeli-server.sh` понимает Docker — с оговоркой.** Он находит контейнер и по
> имени `qeli`, и по `qeli-server` (последнее создаёт комплектный compose), тянет **тот
> образ, на котором контейнер реально запущен**, и пересоздаёт контейнер через
> `docker compose up -d` — простой `docker restart` оставил бы старый образ. Но если образ
> локальный (`qeli:latest`, без реестра), тянуть нечего: скрипт **останавливается с
> объяснением**, а не рапортует об обновлении, которого не было. В этом случае пересоберите
> образ командой выше.

> **Клиентская роль в Docker требует `dns = off`.** `/etc/resolv.conf` в контейнере —
> bind-mount, и дефолтный `dns = tunnel` падает с EBUSY и уходит в реконнект-петлю.
> Entrypoint предупреждает об этом при старте.

### 3.3. Совместимость версий при обновлении

Между клиентом и сервером **нет согласования версий** — нет ни минимальной поддерживаемой
версии, ни отказа по номеру. Совместимость определяется исключительно совпадением
параметров из [§1](#1-что-должно-совпадать-у-клиента-и-сервера). Практический вывод:
обновляйте **сервер первым**, клиенты — по мере возможности; ломается не версия, а
изменившийся дефолт (так было с `bind_static` в 0.7.1 и с `handrolled` позже).

Для перехода dev 0.8.0 на Reality/H2 этот порядок обязателен: новый сервер принимает legacy
Reality carrier и H2, но новый клиент работает только через H2 и не делает downgrade.
Промежуточный reverse proxy/load balancer допустим только как прозрачный TCP pass-through;
TLS termination, H2 conversion или HTTP routing перед qeli ломают discriminator/carrier.

Перед обновлением прочитайте раздел своей версии в [CHANGELOG.md](../../../CHANGELOG.md) —
смена дефолта всегда отмечена там явно.

## 4. Что бэкапить

Бэкап можно снять из панели (**Backup** → скачать архив) или руками. Минимальный набор,
**без которого восстановление невозможно**:

| Что | Путь по умолчанию | В архиве панели | Почему критично |
|---|---|---|---|
| **Identity-ключ профиля** | `/etc/qeli/identity/<профиль>.key` (0600, создаётся при первом старте) | да | Восстановлению **не подлежит**. Потеряете — сервер молча сгенерирует новый при старте, и **все** клиенты с пиннингом получат `SERVER KEY MISMATCH`. Ключ **у каждого профиля свой** |
| Конфиг сервера | `/etc/qeli/server.conf` | да | Профили, порты, режимы, REALITY `short_ids`, `password_hash` панели |
| Пользователи | `/etc/qeli/users.conf` | да | Логины, argon2-хеши, лимиты, ACL, статические IP |
| **Ключ расшифровки `password_enc`** | `/var/lib/qeli/panel-secret.key` | **НЕТ** | Намеренно отделён от зашифрованных паролей в `users.conf`. Без него Argon2-аутентификация продолжит работать, но существующие пароли нельзя повторно выдать в ссылке/QR без сброса |
| TLS-серт и ключ панели | `/etc/qeli/web-tls-{cert,key}.pem` | да | Иначе браузеры снова начнут ругаться на self-signed |
| Ссылки клиентов | `/etc/qeli/client-links/` | да | Готовые `qeli://` и **пароли открытым текстом** — хранить как секрет |
| **Ключ сессий панели** | `/var/lib/qeli/session.key` | **НЕТ** | Под systemd (`StateDirectory=qeli`) лежит **вне** `/etc/qeli`. Потеря не фатальна — разлогинит всех, — но архив панели его не содержит. Без `StateDirectory` используется `/etc/qeli/.session_key` |
| **TOFU-пины клиента** | `/var/lib/qeli/known_hosts` | **НЕТ** | Только на машинах, где qeli работает клиентом |

> **Архив из панели покрывает только `/etc/qeli`.** Всё, что лежит в `/var/lib/qeli`,
> в него не попадает. В частности, он содержит `password_enc` из `users.conf`, но намеренно
> не содержит `/var/lib/qeli/panel-secret.key`, которым эти значения расшифровываются.
> Если снимаете полный бэкап руками — берите оба каталога.

```bash
sudo systemctl stop qeli
sudo tar czf qeli-backup-$(date +%F).tar.gz -C / etc/qeli var/lib/qeli
sudo systemctl start qeli
```

Полезные детали реализации:

- Панель **отказывается** отдать архив, если identity-ключи оказались нечитаемыми (панель
  работает от пользователя `qeli`, а `tar --ignore-failed-read` молча пропустил бы их).
  Вместо битого архива вернётся ошибка с указанием починить права
  (`chown -R qeli:qeli /etc/qeli/identity`) или снимать бэкап от root. Это ровно тот
  случай, когда «бэкап есть, а восстановиться нельзя».
- **Restore сам делает снимок** текущего состояния в `/etc/qeli/.pre-restore-<ts>.tgz`
  (0600, хранятся последние 5) — то есть неудачное восстановление обратимо. Сами эти
  снимки в новый архив не включаются. После restore нужен **ручной перезапуск**.

> Панельный архив содержит приватные identity/TLS-ключи, хеши паролей, `password_enc` и
> клиентские ссылки с паролями открытым текстом. Полный ручной архив дополнительно содержит
> `panel-secret.key` и остальное состояние из `/var/lib/qeli`. Оба варианта храните как
> секрет: на шифрованном носителе, не в общем облаке и не в репозитории.

**Проверьте восстановление заранее**, а не в момент аварии: разверните архив на запасной
машине, поднимите сервер, подключитесь клиентом с пиннингом. Только это подтверждает, что
identity-ключ действительно сохранён.

## 5. Файрвол: что открывать

Минимум — **порт каждого включённого профиля** (`bind.port`, с правильным протоколом) и,
если панель нужна снаружи, её порт.

| Что | Порт по умолчанию | Протокол | Открывать |
|---|---|---|---|
| VPN-профиль | `443` | по `bind.transport` — **TCP или UDP** | всегда |
| Дополнительные профили | 8443–8451 в multiprofile-шаблоне | TCP/UDP по профилю | если включены |
| Веб-панель | `8080` | TCP | **только если** нужна снаружи |

Важные оговорки:

- **UDP-профиль требует UDP-правила.** Открытый TCP/443 не пропустит `udp-quic` на 443 —
  это разные правила в облачном Security Group.
- **DNS наружу открывать не нужно.** Резолвер qeli работает **внутри** туннеля.
- **Панель лучше не публиковать.** Безопаснее оставить `bind = 127.0.0.1` и ходить через
  SSH-туннель: `ssh -L 8080:127.0.0.1:8080 root@сервер`. Если всё же публикуете —
  обязательны `password_hash` (без него публичный bind просто не стартует) и
  `allowed_ips`. `install-qeli-server.sh` оставляет панель **на loopback** и публикует
  её только при `QELI_PANEL_PUBLIC=1` вместе с `QELI_PANEL_ALLOWED_IPS`; публичный bind
  без списка источников он отклоняет — см. §2 GETTING-STARTED.
- **Правила для туннеля qeli ставит сам**, если у профиля включён `routing.nat.enabled`:
  `ip_forward`, MASQUERADE, `FORWARD … ACCEPT` и MSS-clamp, с тегом `qeli-nat:<профиль>`
  и снятием при чистой остановке. Дублировать их вручную не нужно — подробности и
  единственное исключение см. в [CONFIG.md](CONFIG.md), раздел «Тюнинг ОС сервера».
- **iptables-nft и legacy.** qeli работает **только** через CLI `iptables` (никогда `nft`
  или `ufw`) и проверяет результат не по коду возврата, а перечитывая правила (`-C`) —
  на nft-обёртке код возврата врёт. Правила разделены на обязательные (MASQUERADE и два
  MSS-клампа: при неудаче установка откатывается и профиль не стартует) и
  условные (`FORWARD … ACCEPT`: отсутствие безопасно только для пустой цепочки со встроенной
  политикой `ACCEPT`). Если увидите
  в логе `FORWARD ACCEPT rules could not be applied (host has a mixed legacy/nft filter
  table)` — егресс продолжается только после проверки такого empty/`ACCEPT`; `DROP`, любое
  явное правило/jump или непрочитанная цепочка прерывают запуск профиля.
- **OpenWrt.** Там свой файрвол (fw4/nftables): пакет **один раз при установке** создаёт
  зону `qeli` и правило `lan → qeli`. Это сделано именно потому, что сырые iptables-правила
  fw4 вычищает при `/etc/init.d/firewall reload`. Побочный эффект: зона привязана к имени
  устройства на момент установки — **смените `qeli.main.dev` потом, и зона останется
  указывать на старое имя**. Подробности — [qeli-openwrt/README.md](../../../qeli-openwrt/README.md).

Проверить, что именно поставил qeli:

```bash
sudo iptables-save | grep qeli-nat
```

## 6. Тихие ловушки конфигурации

Эти настройки не вызывают ошибок — они просто не делают того, чего вы от них ждёте.
Сервер предупреждает о них в логе **при старте**, поэтому после правки конфига стоит
прочитать первые строки `journalctl -u qeli`.

| Настройка | Когда бесполезна | Что в логе |
|---|---|---|
| `obf.awg.*` (junk) | на TCP-профиле `fake-tls` / `reality-tls` | `obf.awg.enabled has no effect on a TCP '<mode>' profile` — junk шлётся только на TCP-`obfs` и на любых UDP |
| `obf.multipath.*` | на UDP-транспорте | `has no effect on a UDP transport` — бондинг потоков только для TCP, UDP-сессия ограничена одним потоком |
| `web.secure_cookie` | на панели по HTTP | Cookie с флагом `Secure` браузер по HTTP не отправит — вы просто не сможете войти |
| `web.allowed_origins` не задан | панель за прокси/по домену | Страница грузится, но любой POST — 403 (CSRF по Origin) |
| `perf.connection.handshake_timeout_secs = 0` или `perf.connection.max_clients = 0` | всегда | Явный ноль отключает рабочую семантику таймаута/лимита и отвергается при проверке. Удалите ключ, чтобы использовать baseline-дефолт, либо задайте положительное значение |

Отдельно: **опечатка в имени ключа не логируется вообще** — см.
[§2](#2-проверка-конфига-перед-запуском).

## Локальный управляющий сокет

Worker слушает `/var/run/qeli/control.sock`. `QELI_CONTROL_SOCKET` задаёт другой путь
для сервера и значение по умолчанию для CLI; явный `--socket` выбирает путь команды.
Это административный API с доступом по правам ОС. Его служебный JSON не является
форматом конфигурации: конфиги Qeli остаются INI.

В одном network namespace допускается один server worker со всеми профилями.
До preflight, учёта и восстановления firewall он удерживает kernel lease
`qeli.server.worker` (abstract Unix socket); другой control/state каталог, mount
или PID namespace его не обходят. Lease сохраняется во время `post_down`.
Ранняя ошибка до первой сетевой мутации освобождает его; после начала работы
аварийная отмена или неполная очистка удерживает reservation до выхода процесса,
чтобы следующий worker не пришёл поверх незавершённых задач. Штатное успешное
завершение освобождает lease после остальных ресурсов. SIGKILL освобождает
kernel socket, а следующий запуск выполняет обычное восстановление. Для нескольких
worker разделите network namespaces и config/state/control пути; дополнительные
профили одного worker не требуют такого разделения. Обычная пара supervisor +
worker поддерживается. Старые бинарники не участвуют в этой блокировке — остановите
прежний worker перед обновлением.
[Владение](../reports/AUDIT-Q14-WORKER-NETWORK-LEASE.md) ·
[аварийная отмена](../reports/AUDIT-Q25-SERVER-FORCED-DROP-LEASE.md).

Каталог сокета должен принадлежать пользователю worker, иметь режим `0700` и не быть
символической ссылкой. Новый каталог Qeli создаёт закрытым; права существующего не
меняет. Общий `/tmp` нельзя использовать непосредственно: укажите, например,
`/tmp/qeli-<uid>/control.sock`. Предки каталога должны принадлежать root/пользователю
worker и не разрешать чужую запись; shared sticky `/tmp` допускается. Стандартная
ссылка `/var/run` → `/run` поддерживается. Пакетный systemd unit устанавливает
`RuntimeDirectoryMode=0700`; собственный unit должен задавать тот же режим и владельца.
При обновлении бинарника отдельно от unit проверьте настройки runtime-каталога.

Сам сокет получает `0600`. Соседний `control.sock.lock` хранит межпроцессную блокировку
до завершения control handlers и профилей worker. Не удаляйте lock-файл работающего
процесса. Повторный запуск откажется занять используемый путь; обычный файл или symlink
не удаляются. Оставшийся после аварии сокет удаляется только после проверки владельца
и `ECONNREFUSED` от неблокирующего connect. При штатном выходе удаляется только inode
сокета этого worker; lock-файл остаётся для следующих запусков.

Протокол: одна строка JSON на соединение, до 64 KiB запроса и 8 MiB ответа без LF/CRLF.
Переполнение возвращает ошибку вместо использования обрезанного сообщения. Чтение
запроса, connect CLI и запись имеют предел 5 с; чтение ответа CLI — 15 с. Одновременно
обрабатываются до 16 соединений. При остановке приём закрывается, принятые обработчики
завершаются до teardown профилей. CLI worker включает общий 45-секундный бюджет
очистки, supervisor сохраняет 60-секундный grace. Принудительное завершение не
подтверждает завершение команды или хука; см. раздел об остановке ниже.


## Восстановление серверного firewall

`server-firewall.state` в `STATE_DIRECTORY` (по умолчанию `/var/lib/qeli`) хранит точные
NAT/FORWARD/MSS/DNS INPUT/REDIRECT правила до выполнения команд. Это внутренний
журнал; пользовательские конфиги остаются INI. Требуются доступный `SO_NETNS_COOKIE`
и доверенный state каталог: без symlink, чужой записи и небезопасных владельцев.

После SIGKILL запускайте worker с прежним state каталогом в том же network namespace
и с тем же iptables backend. Удалённый из INI профиль также очищается. Для правил,
записанных этой версией, recovery не требует `-S`: используется точная проверка `-C`
и удаление `-D`. Неполная очистка прерывает запуск и сохраняет unresolved записи.
Сначала устраните причину отказа и повторите запуск; не удаляйте журнал или `.lock`.
Пустой журнал и стабильный `.lock` после штатного завершения — нормальное состояние.

При сообщении `iptables backend changed` восстановите исходный выбор nft/legacy
для соответствующего семейства. Журнал не переключает backend автоматически и не
считает отсутствие правила в другом backend успешной очисткой. Повреждение файла,
неизвестная версия или потеря namespace context требуют расследования; удаление
журнала теряет сведения о правилах. Смена `STATE_DIRECTORY` не переносит состояние.

Журнал ограничен 8 MiB, 32768 правилами и 64 namespace-группами. Чужие группы остаются
нетронутыми; после смены boot ID валидные прежние записи больше не исполняются.
Исторические правила старых бинарников без журнала по-прежнему зависят от tagged
sweep и доступного listing. Остановите старый worker перед обновлением.
[Проверки и границы](../reports/AUDIT-Q14-FIREWALL-JOURNAL.md).

## Восстановление клиентского DNS

Managed DNS на Linux также требует `SO_NETNS_COOKIE` и доверенного `/var/lib/qeli` без symlink и group/world write. Per-link DNS state не переносится через `STATE_DIRECTORY`. Перед обновлением штатно остановите старый клиент; оставшиеся v1-маркеры требуют ручного разбора, если совпадают с новым link. [Формат v2 и восстановление](TROUBLESHOOTING.md#650-linux-владение-dns-lease-и-восстановление-маркеров).

Старые глобальные `dns-backup.json`/`dns-holders` не восстанавливаются автоматически: startup сохраняет их и требует ручного разбора даже при `dns = off`/`system`. Перед обновлением штатно остановите старый клиент. [Процедура §6.20](TROUBLESHOOTING.md#620-linux-восстановление-старого-dns-не-удалось-снимок-сохранён).

## Восстановление клиентского kill-switch

Повторная установка Linux kill-switch поверх прежней защиты выполняется под временными DROP-правилами `qeli-ks-rebuild:<tun>`. При ошибке или SIGKILL они остаются; успешный retry снимает их после готовности обеих требуемых семей. Guards могут блокировать DNS/loopback до готовности замены; `allow_ipv*_leak` не обходят отказ восстановления. Для ручного снятия после остановки владельца проверьте guards отдельно от `QELI_KS_<tun>`. [Процедура §6.79](TROUBLESHOOTING.md#679-linux-kill-switch-rebuild-guard-остаётся-после-отказа).

## Linux: физические маршруты после изменений администратором

Клиент удаляет собственный обходной маршрут или blackhole только пока наблюдаемая
запись соответствует его параметрам и неявным значениям. Замена на `proto static`,
другой metric/source/scope либо дополнительные атрибуты сохраняется при остановке.
Сообщение `owned route changed; preserving replacement` означает, что Qeli отказался
от прежнего ownership. Проверьте оставшуюся запись в исходном network namespace:
она теперь требует решения администратора. Подходящий маршрут, существовавший до
подключения, используется без права точечного удаления.

Собственный managed TUN по-прежнему очищается целиком при завершении. Проверка не
атомарна с последующей командой и не различает идентичные маршруты другого root.
Подтверждённые физические записи сохраняются в постоянном журнале для следующего
запуска после SIGKILL; неопределённый intent требует ручного разбора. Не очищайте
таблицу маршрутов целиком; перед ручным удалением установите происхождение записи.
[Проверки и ограничения](../reports/AUDIT-Q25-ROUTE-ATTRIBUTES.md).

## Восстановление физических маршрутов клиента

Linux-клиент с managed TUN сохраняет физические bypass/exclude и blackhole в
`/var/lib/qeli/client-routes.state`. Требуются `SO_NETNS_COOKIE` и доверенный каталог,
доступный для записи владельцу процесса, без symlink и group/world write. Это
требование действует также при `dns = off`/`system`. `STATE_DIRECTORY` не меняет путь.
Все клиенты в одной сети должны видеть общий каталог и `client-routes.state.lock`.
Конфиги остаются INI; журнал — внутреннее состояние восстановления.

Перед обновлением штатно остановите старый клиент. После SIGKILL запускайте с прежним
`dev`, в исходном network namespace и с прежним каталогом состояния. Recovery идёт до
DNS resolution/handshake. Оно удаляет только подтверждённые записи, которые сохранили
исходные атрибуты; операторские замены остаются. Чужие namespace/TUN группы не очищаются.
Существующий persistent/live TUN блокирует recovery; Qeli не удаляет его по имени.

Неопределённый intent не даёт права удалить совпавший маршрут. При неполном recovery
запуск прекращается, записи сохраняются. Устраните причину и повторите запуск; порядок
ручного разбора описан в [§6.81](TROUBLESHOOTING.md#681-linux-восстановление-журнала-физических-маршрутов).
Не удаляйте журнал и lock для обхода отказа. Пустой файл состояния и lock после чистой
остановки нормальны. Журнал не усыновляет остатки версий, которые его не записывали.
Лимиты: 8 MiB, 128 групп, 8192 записи. Attach не управляет этими маршрутами.
[Проверки и границы](../reports/AUDIT-Q25-ROUTE-JOURNAL.md).

## Persistent TUN/TAP после аварии клиента

Qeli не удаляет сохранившееся устройство и не присваивает его по совпадению имени.
После остановки владельцев подтвердите происхождение остатка, сохраните evidence,
при необходимости удалите только его вручную и повторите запуск в прежнем контексте.
До завершения восстановления сохраняйте kill-switch и журналы. Подробная процедура
и ограничения: [§6.82](TROUBLESHOOTING.md#682-linux-persistent-tuntap-пережил-остановку-клиента).

## Совместная работа с nftables и firewalld

При crash recovery сохраняйте исходный backend отдельно для IPv4 и IPv6. Нативные
правила могут мешать подтверждению отсутствия даже после успешного удаления; Qeli
сохраняет такие записи и требует устранить ошибку проверки. Reload firewalld не
заменяет восстановление журнала Qeli. Проверка сохранения правил и проверка реального
трафика через зоны/политики — разные этапы.
[Диагностика §6.83](TROUBLESHOOTING.md#683-linux-mixed-nftlegacyfirewalld-recovery).

Разрешающее правило Qeli в iptables/ip6tables не отменяет DROP другой nftables/firewalld
цепочки. Администратор настраивает зоны и политики для WAN/TUN, VPN listener,
транзита и DNS. В режиме `manual` он также обеспечивает IPv6 forwarding,
INPUT и доставку DNS с порта 53, если DNS proxy включён. Qeli сохраняет чужие
запреты при stop/restart; снятие блокировки выполняется через её владельца.
Четыре mixed backend с четырьмя IPv6-профилями и public policy прошли reload/restart
и реальные контрольные IPv4/IPv6 пробы разрешённого/запрещённого порта; это не
гарантия трафика через любую администраторскую политику.
[Объём проверки](../plans/AUDIT-DEBT.md).

Сохраняйте исходный backend обоих семейств до завершения клиентского recovery/stop.
Точное предупреждение о наличии legacy-таблиц допустимо вместе с известным сообщением
об отсутствии правила/цепочки; неизвестные ошибки не игнорируются. Не очищайте чужие
таблицы, чтобы убрать это предупреждение. [Клиентская диагностика §6.84](TROUBLESHOOTING.md#684-linux-клиент-отказывает-при-предупреждении-о-legacy-таблицах).

## Остановка при задержке DNS

Общий клиентский резолвер ограничивает ожидание и число DNS/NSS-вызовов. SIGTERM/SIGINT
прерывают ожидание Linux-клиента при установке/refresh kill-switch и начальном подключении;
снятие сетевых настроек остаётся проверяемой операцией. Четыре зависших системных вызова
занимают все слоты до завершения; поздний ответ не запускает настройку сети.
[Диагностика §6.85](TROUBLESHOOTING.md#685-клиент-задержка-dns-и-остановка).

## Resolver-файлы перед установкой защиты

Linux kill-switch заранее читает `/run/systemd/resolve/resolv.conf` и `/etc/resolv.conf`
одним снимком для IPv4/IPv6. Чтение делит четыре слота с DNS/NSS и входит в общий срок
установки; это ожидание остаётся даже при числовом адресе сервера. Файл должен быть
обычным, не более 64 KiB, список — не более 64 уникальных записей. Повреждённый или
непрочитанный файл не даёт DNS-разрешений; предел общего списка прерывает установку.
Нужен отдельный токен `nameserver`, комментарий после адреса отделяется пробелом.
Scoped IPv6 с `%interface`/`%index` не создаёт разрешение без привязки к интерфейсу и
не мешает другим корректным записям. Изменения DNS после снимка не обновляют firewall
автоматически. [Чтение resolver-файлов](../reports/AUDIT-Q25-RESOLVER-FILES.md).

[§6.86](TROUBLESHOOTING.md#686-linux-resolver-файл-и-разрешения-dns-в-kill-switch).

## Остановка во время применения NetworkPlan

Linux применяет NetworkPlan в отдельном потоке и сохраняет владельцев TUN/маршрутов/DNS
до завершения операции и возможного отката. Обычный SIGTERM/SIGINT обрабатывается во
время ожидания. Уже начатая системная операция не обрывается: клиент ждёт её завершения
и откатывает непринятый результат. До успешного ACK состояние остаётся `awaiting_network`;
отмена до ACK не запускает `post_up`. Ошибка очистки запрещает успешный restart.

Не считайте готовностью к повторному использованию TUN сам факт отправки сигнала.
Дождитесь выхода и проверьте итог очистки. Принудительное уничтожение future может
синхронно ждать присоединения worker; единого предельного срока shutdown пока нет.
[Проверки и границы](../reports/AUDIT-Q25-NETWORK-TASK.md).

## Остановка установленного Linux-туннеля

TCP и UDP используют общий порядок: остановить задачи соединения → восстановить DNS →
остановить и присоединить TUN packet workers → очистить свои маршруты и forwarding →
закрыть исходный TUN descriptor. DNS/routes/forwarding выполняются в отдельном потоке;
клиент ждёт его завершения. Ошибка одной стадии не отменяет остальные попытки очистки.

При сообщении `network resource cleanup reported failure` автоматический reconnect
запрещён, а включённый kill-switch сохраняется. Успешный повтор очистки внутри guard
не превращает первоначальный отказ в успешный выход. Сохраните журналы и проверьте
причину перед новым явным запуском. Принудительный Drop может синхронно ждать завершения;
единого жёсткого срока shutdown пока нет.
[Устройство и проверки](../reports/AUDIT-Q25-TUN-TEARDOWN.md).

## Остановка во время установки, обновления или снятия kill-switch

До изменения firewall остановка может отменить DNS/read-only подготовку. Если операция
уже началась, клиент дожидается её результата. Успех после сигнала переводит setup/refresh
в обычную очистку без нового подключения; ошибка остаётся ошибкой и требует проверки.
Принудительное уничтожение future также ждёт worker, но может блокировать вызывающий поток.

`firewall unhook failed; chain retained` означает, что удаление всех переходов в указанную
цепочку не подтверждено. Qeli сохраняет её содержимое, включая DROP, и возвращает ошибку.
Не очищайте такую цепочку вручную, пока её переходы не проверены. Другую семью firewall
к этому моменту уже могли снять; одна сохранённая цепочка не подтверждает защиту всего
хоста. После устранения причины новый явный запуск выполняет штатный recovery.
[Проверки и границы](../reports/AUDIT-Q25-FIREWALL-TASK.md).

## UDP-сервер с несколькими локальными адресами

При wildcard `bind.address = 0.0.0.0` или `::` ответ уходит с адреса, на который пришёл
пакет клиента. Это относится к handshake, данным и контрольным сообщениям; отдельной
INI-настройки не требуется. Соседние клиенты на разных адресах не меняют источник друг
друга. Если ОС не предоставляет корректный pktinfo, сервер не подбирает другой адрес.
[Проверки и ограничения](../reports/AUDIT-Q15-UDP-LOCAL-ADDRESS.md).

## Остановка во время стартового recovery Linux-клиента

До подключения Qeli резервирует сетевой lease, восстанавливает свои физические
маршруты и проверяет DNS-маркеры в отдельном присоединяемом потоке. SIGTERM/SIGINT
не прерывает уже начатое восстановление: клиент ждёт результат, сохраняя lease.
Успех после stop завершает клиент без нового подключения; ошибка остаётся `failed`.
При `dev_attach = true` восстановление физических маршрутов пропускается, проверка
DNS остаётся. Recovery не переключает живой resolver по одному сохранённому маркеру.

Дождитесь выхода клиента и проверьте итоговую ошибку перед повторным запуском.
15-секундный бюджет route-операции не является общим жёстким сроком shutdown;
принудительный Drop может синхронно ждать worker.
[Проверки и границы](../reports/AUDIT-Q25-STARTUP-RECOVERY-TASK.md).

## Отказ запуска TUN packet workers в Linux-клиенте

`TUN packet pump startup failed` означает отказ запуска обработки пакетов после
применения сетевого плана. Qeli ждёт частично запущенные потоки и очистку своих ресурсов
в присоединяемом worker. Ожидание этой очистки не блокирует соседние async-задачи.
При сообщении об ошибке очистки kill-switch сохраняется; проверьте журналы перед новым
явным запуском. Сигнал остановки не скрывает такой отказ очистки.

Успешный `post_up` подтверждает применение NetworkPlan, но не завершение запуска pump.
При невозможности создать cleanup worker или принудительном Drop аварийное ожидание
может оставаться синхронным. [Проверки и границы](../reports/AUDIT-Q25-PUMP-START.md).

## Диагностика Linux-клиента на медленном хранилище

При заданном `QELI_CLIENT_STATUS` статус записывает один отдельный поток. Пока запись
занята, сохраняется только последний ожидающий снимок; промежуточные состояния могут
не появиться в файле. Формат schema 1 и права `0600` не меняются.

Штатный выход ждёт итоговую запись после остановки sampler. Медленный fsync не блокирует
соседние async-задачи, но может задержать выход процесса; общего жёсткого срока нет.
Ошибки диагностики не меняют результат VPN. Если запись не удалась, файл может быть
устаревшим: проверяйте код выхода и журнал. [Проверки и границы](../reports/AUDIT-Q25-STATUS-WRITER.md).

## Файлы идентичности Linux-клиента

`/var/lib/qeli/device-id` (`QELI_DEVICE_ID_FILE`) читается один раз до подключения.
Сохраняются первые 16 байт прежнего файла, если они не все нулевые. При отсутствии
доступного хранилища временный ID остаётся одним и тем же до выхода клиента, включая
reconnect; после перезапуска он может смениться. Ожидание lock ограничено 15 секундами.
Stop ждёт уже начатую операцию и затем не начинает подключение.

TOFU-файл `/var/lib/qeli/known_hosts` (`QELI_KNOWN_HOSTS`) должен быть обычным UTF-8
файлом не более 1 MiB. Ошибку чтения, повреждённый пин целевого сервера и противоречивые
дубликаты нельзя обойти `allow_unpinned_tofu`. Сохраните исходный файл и проверьте ключ
сервера перед исправлением. Новый пин записывается атомарно с `0600`. Файловый TOFU выполняется в отдельном
присоединяемом worker. Stop/timeout прекращают ожидание handshake; уже принятая запись
завершается до reconnect или выхода. Поздняя ошибка сохраняет результат `failed`,
успешная запись может сохранить пин после отмены. 15 секунд ограничивают flock, а не
весь shutdown. [Worker и отмена](../reports/AUDIT-Q25-IDENTITY-WORKER.md).
[Устройство и проверки](../reports/AUDIT-Q25-IDENTITY-FILES.md).

## Чтение INI при запуске Linux-клиента

Обработчики SIGTERM/SIGINT устанавливаются до открытия конфига. Чтение, начальные
проверки возможностей и определение пути для hooks выполняются в присоединяемом потоке.
Клиентский INI ограничен 256 КиБ: размер обычного файла проверяется до чтения содержимого.
Права для предупреждения о доступности пароля берутся из того же открытого снимка.

При stop во время уже начатого чтения Qeli ждёт его завершения. Успех завершает клиент
без запуска password_command, device-id, подключения или настройки сети; поздняя ошибка
чтения остаётся ошибкой выхода. Это не жёсткий timeout файловой системы: зависший системный
вызов может задержать выход, но обычное ожидание не блокирует async-задачи.
Серверный лимит этим изменением не устанавливается.

## Общий командный срок NetworkPlan и очистки

Настройка Linux NetworkPlan делит **15 секунд** между командами TUN, gateway,
маршрутов и DNS. Компонент может сократить оставшееся время, но не начать свои
15 секунд заново. После исчерпания срока новые команды не запускаются, успешный
NetworkPlan не подтверждается.

Очистка получает отдельные **15 секунд** от первой очистки ресурсов текущей попытки.
Этот срок общий для DNS, ожидания pump, routes, gateway и последующего удаления
kill-switch. Автоматический повтор через Drop использует тот же остаток. Следующая
попытка подключения получает новый срок только после завершения предыдущих владельцев;
накопленные ошибки очистки этим не сбрасываются и запрещают обычный reconnect.
При ошибке очистки ресурсов код не переходит к снятию kill-switch. Если отказ произошёл
уже внутри снятия firewall, часть правил могла быть удалена: полная защита не обещается.

Это срок команд и их admission, а не жёсткий срок выхода процесса: kernel/filesystem I/O,
join packet workers, TOFU/status writers и пользовательские hooks не обрываются этим
таймером. Их ожидание расходует время уже начатой очистки. При timeout проверьте журнал
и остатки в исходном namespace; не удаляйте сохранённые сведения о владельцах для обхода
ошибки. [Проверки и остаток аудита](../plans/AUDIT-DEBT.md).

После timeout gateway и выхода процесса повторный запуск может упереться в `lost live per-interface sysctl evidence`: исходный TUN уже закрыт, а старое значение нельзя переносить на новый одноимённый интерфейс. Это требует [ручного восстановления §6.64](TROUBLESHOOTING.md#664-потерян-исходный-sysctl-интерфейса), а не цикла restart.


## Один Linux-клиент на процесс

Публичный `run_client` допускает один активный запуск на процесс, включая чтение
INI, подключение, очистку и итоговую диагностику. Второй одновременный вызов получает
`a Linux client is already running in this process` до чтения конфига и регистрации
обработчиков сигналов. Адреса carrier и флаг переключения сбрасываются только после
успешного допуска. Для независимых Linux-клиентов нужны отдельные процессы; ограничения
совместного namespace/TUN/kill-switch по-прежнему действуют.

После возврата `run_client` (успеха или ошибки) следующий вызов разрешён; это не отменяет
проверку оставшихся сетевых ресурсов. Для штатной остановки используйте SIGTERM/SIGINT
и дождитесь возврата. Если принудительно уничтожить уже запущенную future, например
через `JoinHandle::abort`, внешний timeout или panic, новые вызовы в этом процессе
получат `previous Linux client was cancelled before cleanup completed; restart the process`.
Вложенные задачи получают запрос отмены, но их async join в Drop не гарантирован;
нельзя начинать новое поколение поверх ещё завершающихся задач. Неопрошенная future
не захватывает допуск. Правило относится к Linux runtime `run_client`, а не ко всем
экземплярам общего transport-core на других платформах.


## Файловые операции hooks и backup

Linux-hooks выполняют проверку metadata скрипта, создание приватного context-файла,
команду и удаление файла на одном присоединяемом потоке с собственным async runtime.
Обычное ожидание не блокирует executor клиента/сервера. При отмене во время подготовки
уже начатый файловый вызов завершается, файл удаляется, команда не запускается. При
отмене работающей команды поток останавливает её группу и дожидается сбора shell до
удаления файла. Принудительный Drop ждёт поток синхронно; он может ждать файловую
систему дольше 30 секунд. Deadline команды/вывода остаётся 30 секунд после подготовки.
Фоновая служба, намеренно отделённая hook с закрытыми pipes, сохраняет прежний контракт.

Backup панели читает и проверяет активный конфиг в blocking worker, удерживающем
блокировку конфигурации до окончания работы даже при отмене HTTP-запроса. Чтение
использует общий загрузчик стабильного обычного файла: FIFO отвергается без ожидания
писателя. Подготовка расходует тот же общий бюджет 60 секунд, что создание/проверка
архива; поздний результат не запускает tar и не публикует backup. Зависший syscall
невозможно безопасно оборвать этим таймером. Формат INI, права hooks, состав архива и
правила restore не меняются. [Проверки и остаток аудита](../plans/AUDIT-DEBT.md).

## Остановка клиентских туннелей панели

При обработке SIGTERM/SIGINT supervisor сразу закрывает Connect/autostart.
Worker и уже запущенные клиенты получают запрос остановки параллельно: ожидание
worker не откладывает остановку клиентов и не добавляет к ней новый grace.
Клиенты делят общий пятисекундный grace с момента запроса остановки; он не
продлевается при повторном ожидании. Клиент, не завершившийся в срок, получает
SIGKILL и присоединяется до освобождения его дескриптора процесса. Принудительный
kill или неуспешный exit дают ошибку остановки supervisor: восстановление DNS,
маршрутов и firewall этим исходом не подтверждено. При следующем запуске действуют
обычные механизмы восстановления принадлежащих Qeli ресурсов.

Отмена HTTP-запроса Disconnect не теряет процесс и не допускает его замену до
завершения очистки. Статус остальных клиентов остаётся доступным. Этот grace
не является общим сроком остановки сервера и не прерывает зависший kernel syscall.

## Принудительная отмена серверного профиля

При отмене future профиля Qeli закрывает приём дочерних задач и сохраняет вместе
их JoinSet, TUN и DNS/NAT-ресурсы. Worker сначала присоединяет дочерние задачи,
затем удаляет ресурсы; итоговая NAT-очистка и hooks выполняются после этого.
Отмена ожидания очистки возвращает поколение в очередь worker и сохраняет ошибку:
успешный последующий join не превращает принудительную отмену в штатную остановку.

Для остановки используйте SIGTERM и дождитесь выхода. Уничтожение самой future
worker не гарантирует завершение очистки: незавершённые ресурсы и допуск к
network namespace остаются удержаны до выхода процесса. Не запускайте новое
поколение в том же процессе. Следующий процесс использует обычное восстановление
принадлежащих Qeli правил. Ограничение CLI-процесса описано ниже; библиотечный
`run_worker` не устанавливает этот таймер. [Проверки](../plans/AUDIT-DEBT.md).

## Общий бюджет остановки сервера

CLI worker (`_worker`, в том числе запущенный supervisor) включает один бюджет
**45 секунд** при первом наблюдаемом stop или fatal-событии, до его записи в журнал.
В него входят control handlers, сервисные и профильные задачи, deferred joins,
NAT/sysctl-очистка, hooks, запись счётчиков и удаление control socket. Повторное
ожидание не продлевает срок. Таймер работает в отдельном системном потоке и не
зависит от исполнения Tokio-задач. Лимит меньше 60-секундного grace supervisor,
чтобы worker мог сам сообщить ошибку до принудительного kill родителем.
Штатный выход подтверждает итоговый результат
очистки; ошибка даёт ненулевой код.

При истечении срока worker закрывает допуск системных команд, отправляет SIGKILL
учтённым группам ещё не собранных принадлежащих ему команд и завершает процесс
с **кодом 124**. Supervisor сообщает `worker exceeded its total shutdown budget`:
это ошибка, очистка не подтверждена. Журналы владения сохраняются для обычного
восстановления при следующем запуске. Не удаляйте их, чтобы скрыть ошибку.
Фоновые службы, намеренно отделённые hook с закрытыми pipe, сохраняют прежний
контракт; потомки, покинувшие группу процессов, не управляются Qeli.

Supervisor одновременно останавливает worker, клиентов панели и свою очередь
уведомлений: grace worker остаётся **60 секунд**, клиентов — **5 секунд**,
уведомлений — **10 секунд** от первого запроса остановки. Уведомления worker
также завершаются параллельно его очистке; отдельные десять секунд после неё
не добавляются. Принятые сообщения могут потеряться при timeout/аварийном выходе.

45 секунд относятся к фазе очистки CLI, а не к моменту доставки сигнала ОС,
подготовке до входа в shutdown или библиотечному `run_worker`. Библиотечная отмена
сохраняет ресурсы и блокирует повторный in-process запуск по описанному выше
контракту. Произвольные зависшие kernel syscalls, kernel exit/reaping и синхронный
spawn под защитой реестра команд нельзя безопасно прервать этим таймером;
абсолютная гарантия времени при отказе ядра не даётся. Наблюдаемый зависший
файловый worker проверен аварийным выходом и последующим восстановлением.

## Системный контекст Linux-клиента

Для независимых CLI-клиентов используйте отдельные процессы. Один `run_client`
удерживает process admission до конца штатной очистки; после принудительного Drop
нужен перезапуск процесса. Для `dns = tunnel` клиент и resolver должны находиться
в поддерживаемом общем network/PID контексте; смена владельца D-Bus не даёт Qeli
права менять настройки новой службы. При `dev_attach = true` внешний менеджер
сохраняет устройство и packet features стабильными на время attach, а sysfs
соответствует текущему network namespace. Проверка индекса отклоняет обнаруженную
подмену, но совпадение числовых индексов разных namespace не доказывает identity.

Поздний IPv4 default route или глобальный IPv6 не снимает уже установленный
kill-switch: это проверено на четырёх сочетаниях nft/legacy. Выбранный WAN нельзя
удалять/заменять с сохранением имени при активном профиле; сначала остановите
профиль и подтвердите cleanup. Монитор смены default WAN по имени не устраняет
это ограничение. [Проверки и остаток D06](../plans/AUDIT-DEBT.md).
